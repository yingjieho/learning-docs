# Aurora PostgreSQL vs. RDS-for-PostgreSQL — WAL & Logical Slot Replication

> **Status:** Draft for discussion
> **Date:** 2026-07-26
> **Author:** yingjie.ho@merquri.io
> **Related:** — (standalone comparison; no companion docs)
> **Scope:** WAL and logical replication slot behavior only, as it affects a CDC consumer (Debezium, PeerDB, native subscriber). Not a general performance/cost comparison.

## 1. Overview

Weighs Aurora PostgreSQL against RDS-for-PostgreSQL strictly as the **source engine for WAL-based logical replication / CDC** — the slot a Debezium/PeerDB/native subscriber streams from. Each row of §2 is a direct head-to-head on one dimension; rows marked **"Same"** carry no material difference between the engines.

## 2. Head-to-head comparison

| Dimension | Aurora PostgreSQL | RDS-for-PostgreSQL | Caveat | Impact | Mitigation | Better choice |
|---|---|---|---|---|---|---|
| **WAL storage & decode path** | • WAL offloaded to a shared, multi-AZ distributed storage layer<br>• Readers share that storage and hold **no independent WAL copy**<br>• Logical decode reads WAL **back** from storage (retrofit) | • Community Postgres with **local-disk (EBS) WAL**<br>• Physical standbys each keep their **own** WAL copy<br>• Logical decode reads local WAL directly | • *(Aurora)* Logical decoding is retrofitted onto a storage engine not built around WAL → the root of every Aurora-specific caveat below<br>• *(RDS)* Inherits community behavior, including community's own limits | • *(Aurora)* Extra decode surface to reason about, version-pin, and monitor<br>• *(RDS)* Behavior predictable straight from upstream Postgres docs | • *(Aurora)* Track AWS release notes for decode-path changes per minor<br>• *(RDS)* Follow community PostgreSQL guidance | **RDS** — fewer moving parts; behavior is community-predictable |
| **Data integrity — write-through cache** | • `rds.logical_wal_cache` **ON by default** (PG ≥ 14.5/13.8/12.12/11.17)<br>• **Known incompatibility with external CDC tools** (Debezium, Airbyte, Oracle GoldenGate) — a **WAL-sender error** (notably on **large transactions**) that makes the capture process **error/disconnect**, not a silent drop<br>• AWS acknowledged the Debezium case; GoldenGate documents it as **bug 36104153**; a compatibility surface to pin & monitor | • **No write-through cache** in the CDC path<br>• No equivalent CDC-tool incompatibility surface | • *(Aurora)* The default-on cache can break external CDC decoding — a **loud error / incompatibility**, not a silent healthy-pipeline loss<br>• *(RDS)* Caveat N/A — no such cache | • *(Aurora)* CDC capture **errors/disconnects** until the cache is disabled — **loud and recoverable**; missed-event risk is **tool/version-dependent** | • *(Aurora)* Set `rds.logical_wal_cache = 0` + restart writer (AWS-recommended; **AWS states this loses no existing data**), **or** pin a connector-validated minor<br>• *(Aurora)* Reconcile source↔target row counts to be safe | **RDS** — no write-through-cache incompatibility to manage |
| **Replication lag** | • Cache skips the storage round-trip → up to **17× lower lag**<br>• With the cache off, decode is slower (round-trips to storage) | • Lag tracks community Postgres; no cache to tune | • *(Aurora)* The 17× reduction depends on the **same cache** that carries the CDC-tool incompatibility risk<br>• *(Aurora)* **Conditional:** if a connector forces the cache **off** (see Data-integrity row), this advantage **disappears** — Aurora reverts to the slow storage round-trip and **RDS leads on lag**<br>• *(RDS)* No lag knob to tune | • *(Aurora)* Disabling the cache **raises lag up to ~17×** (AWS pgbench best-case) — reverts to the storage-round-trip decode path; absolute lag scales with write rate / transaction size<br>• *(vs RDS)* Cache-off Aurora is **slower than RDS** at CDC, since RDS's local-disk WAL decode has no round-trip — tolerable for lag-relaxed analytics CDC, a risk for near-real-time SLAs | • *(Aurora)* Prefer a connector-validated minor to keep the cache **and** compatibility; size expectations for higher lag if it must be off | **Aurora** if cache on & connector-compatible; **RDS** if the cache is forced off |
| **Failover — slot survival (pre-PG17)** | • Slot exists **only on the writer**; readers don't carry it<br>• Promotion **destroys the slot** → CDC stops → full re-snapshot | • Physical standbys make behavior track community Postgres<br>• Failover far less likely to force a re-snapshot | • *(Aurora)* Readers hold no slot, so a promotion leaves the new writer with no slot to resume from<br>• *(RDS)* Slot state travels with physical standbys | • *(Aurora)* CDC halts on every failover; full re-snapshot; data gap until reseed completes | • *(Aurora)* Move to PG17+ failover slots (next row)<br>• *(Aurora)* Otherwise: documented re-snapshot runbook + failover alerting | **RDS** — slot survives failover natively |
| **Failover — slot survival (PG17+) & setup burden** | • `failover=true` + `sync_replication_slots` propagate the slot to readers → survives promotion<br>• Aurora **manages** the sync plumbing<br>• Consumer reconnects via the cluster endpoint<br>• Exact parameter surface under-documented | • Same flags, but **wired manually** via parameter groups: `synchronized_standby_slots`, `hot_standby_feedback=1`, `rds.logical_slot_sync_dbname`<br>• Post-failover: `ALTER SUBSCRIPTION … CONNECTION` to the new instance | • *(Both)* No-gap holds **only if the slot synced before** failover<br>• *(RDS)* Manual param wiring can be misconfigured silently<br>• *(Aurora)* Param surface under-documented per minor | • *(Both)* A new/lagging replica resumes from a **stale LSN** → gap or re-snapshot<br>• *(RDS)* Silent misconfig → slot never actually synced despite looking enabled | • *(Both)* Enable the flags, then **verify** the slot is present & synced on the replica before a failover drill<br>• *(RDS)* Validate every param; *(Aurora)* validate against the target minor | **Aurora** — managed sync vs. RDS manual wiring |
| **HA — failover speed & read scaling** | • Fast automated failover<br>• Read autoscaling over shared storage | • Slower failover<br>• Read replicas available but less elastic | • *(Aurora)* Fast HA does nothing for **CDC continuity** if the slot itself doesn't survive the failover | • *(Aurora)* On pre-PG17, the HA advantage doesn't reduce CDC recovery cost (still a re-snapshot) | • *(Aurora)* Pair HA with PG17 failover slots so fast failover also means fast CDC resume | **Aurora** — faster failover, elastic reads |
| **Stalled-slot failure mode** | • Storage **auto-grows to 256 TiB** (engine ≥ 17.5/16.9/15.13) → never hits disk-full<br>• Failure is **silent** — no capacity ceiling to trip an alarm | • Retained WAL fills the **provisioned EBS volume** → disk-full → **writes stop** (OLTP outage) unless autoscaling is on & under the ≤ 64 TiB cap<br>• Failure is **loud** — disk-pressure alarms fire first | • *(Aurora)* Auto-grow removes the disk-full ceiling → **no early-warning signal**<br>• *(RDS)* A stalled slot marches toward a hard write-stop | • *(Aurora)* Stall goes unnoticed → resurfaces later as cost or wraparound<br>• *(RDS)* Disk-full = OLTP **write outage** | • *(Both)* Alert on slot lag / retained-WAL bytes<br>• *(RDS)* Provision headroom + storage autoscaling<br>• *(Aurora)* Don't treat capacity as a health signal | **Trade-off** — RDS fails loud (catchable); Aurora avoids the write outage |
| **XID wraparound** *(idle slot pins `xmin` → blocks VACUUM)* | • No disk-full alarm → wraparound stays **hidden** until protective read-only shutdown<br>• Only slot-lag / `xmin`-age metrics catch it | • Same wraparound endpoint<br>• Disk-pressure usually surfaces the stall before wraparound | • *(Both)* An idle slot pins `xmin`, blocking VACUUM from advancing the XID frontier<br>• *(Aurora)* No disk-full alarm to catch it early | • *(Both)* Table/catalog bloat en route, then a **protective read-only shutdown** (hard OLTP outage) | • *(Both)* Alert on oldest-slot `xmin` age well before the limit<br>• *(Both)* Set `max_slot_wal_keep_size` deliberately (it can invalidate the slot) | **RDS** — disk-pressure surfaces it before wraparound |
| **Storage scaling & cost** | • Elastic auto-scaling, no provisioning<br>• **High-water-mark billing**: cost does not drop when WAL frees (reclaim ~10 TB/day) | • Provisioned volume, capped ≤ 64 TiB<br>• **Predictable cost**; freed space reflected immediately | • *(Aurora)* High-water-mark billing persists **after** WAL frees<br>• *(RDS)* The ≤ 64 TiB cap is a hard ceiling, not just a cost line | • *(Aurora)* Bill spike **outlives** the incident (reclaim ~10 TB/day)<br>• *(RDS)* Hitting the cap becomes an **outage**, not merely cost | • *(Aurora)* Add a storage-cost alarm; expect reclaim lag<br>• *(RDS)* Capacity-plan + enable autoscaling under the cap | **Trade-off** — Aurora scales elastically; RDS cost is predictable |
| **Major-version upgrade & slots** | • Same gate as RDS<br>• **Compounds** with the pre-PG17 failover-slot loss above<br>• PG17 `pg_upgrade` preserves slots only for upgrades starting **from** 17 | • Upgrade pre-check **fails while any slot exists** (including inactive)<br>• Must drop → upgrade → recreate → re-snapshot if changes were in flight at drop time | • *(Both)* Any existing slot — **even inactive** — blocks the upgrade pre-check<br>• *(Aurora)* Compounds with failover-slot loss | • *(Both)* Upgrade blocked until slots dropped; in-flight changes at drop time are **lost → full re-snapshot** | • *(Both)* Divert writes → confirm full consumption → drop slots → upgrade → recreate<br>• *(Both)* Remove forgotten inactive slots first | **RDS** — same gate, no failover-slot compounding |
| **Enablement** | • Same as RDS | • `rds.logical_replication` is **static** → parameter group + reboot<br>• Needs `rds_replication` role and `max_replication_slots` / `max_wal_senders` tuning | • *(Both)* Turning on logical replication is **not a runtime toggle** — the static param needs a reboot | • *(Both)* Enabling CDC requires planned downtime/restart | • *(Both)* Enable in a maintenance window; set `max_replication_slots` / `max_wal_senders` and the `rds_replication` role up front | **Tie** — identical behavior |
| **`REPLICA IDENTITY`** | • Same as RDS (community behavior) | • UPDATE/DELETE need a **PK or `REPLICA IDENTITY FULL`** for before-images<br>• Otherwise updates/deletes are silently mishandled downstream | • *(Both)* Without a PK / `REPLICA IDENTITY FULL`, UPDATE/DELETE carry no usable before-image | • *(Both)* Updates/deletes silently mishandled → **wrong analytics**, no error raised | • *(Both)* Audit every replicated table pre-CDC; add a PK or set `REPLICA IDENTITY FULL` (mind the extra WAL cost of FULL) | **Tie** — identical behavior |
| **Cross-region replication** | • Aurora Global Database restricts logical replication to the **primary-region writer** | • No logical-replication-specific cross-region restriction | • *(Aurora)* Global Database confines logical replication to the primary-region writer<br>• *(RDS)* No such restriction | • *(Aurora)* Cannot drive CDC from a secondary region as might be assumed | • *(Aurora)* Source CDC from the primary-region writer; confirm topology & version support before relying on it | **RDS** — no cross-region restriction |

## 3. Summary — which to choose for what

Across the 13 dimensions the **Better choice** column tallies **RDS 6 · Aurora 3 · Trade-off 2 · Tie 2**. The split is not random: RDS wins the **correctness and operational-safety** dimensions, Aurora wins the **performance, HA, and scaling** dimensions. The choice therefore follows the workload's dominant priority.

| Priority driving the decision | Better choice | Because (from §2) |
|---|---|---|
| **CDC data integrity above all** | **RDS** | No write-through-cache CDC-tool incompatibility to work around; no proprietary decode path to pin/monitor |
| **Lowest operational surprise** | **RDS** | Loud (not silent) stalled-slot failure; wraparound surfaces via disk-pressure; no failover-slot loss to engineer around |
| **Minimal replication lag** | **Aurora** (cache on & connector-compatible) | Write-through cache → up to 17× lower lag; **flips to RDS** if a connector forces the cache off |
| **Fast failover + read/storage elasticity** | **Aurora** | Fast automated failover, read autoscaling, storage auto-grows to 256 TiB |
| **Least CDC-recovery work on failover (PG17+)** | **Aurora** | Managed slot synchronization vs. RDS's manual parameter-group wiring |
| **Predictable storage cost / no silent bill growth** | **RDS** | Provisioned volume; freed WAL space reflected immediately (Aurora bills at high-water mark) |

**Net recommendation:**
- **Default to RDS-for-PostgreSQL** when the source's job is to feed a CDC pipeline reliably and the team wants community-standard, loud-failing, low-surprise behavior — the majority of dimensions favor it.
- **Choose Aurora PostgreSQL** when its HA/scaling/latency profile is independently required, **and** commit to the mitigations that neutralize its CDC caveats: pin a connector-validated minor (or disable the write-through cache), run **PG17+ with failover slots**, and alert on `xmin` age + storage cost since capacity no longer self-warns.
- The two **Trade-off** rows (stalled-slot failure mode, storage scaling vs. cost) are the ones to decide by context — pick RDS if an early-warning signal matters more than avoiding a write-stop; pick Aurora if avoiding the OLTP outage and scaling elastically outweigh cost predictability.
