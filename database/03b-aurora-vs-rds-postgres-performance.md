# Aurora PostgreSQL vs. RDS-for-PostgreSQL — OLTP Performance

> **Status:** Draft for discussion
> **Date:** 2026-07-25
> **Author:** yingjie.ho@merquri.io
> **Related:** [`03a-aurora-vs-rds-postgres-wal.md`](./03a-aurora-vs-rds-postgres-wal.md) — WAL / logical-slot / CDC comparison (companion; the reliability counterpart to this performance doc)
> **Scope:** Runtime performance for a **pure OLTP** workload — many small, concurrent, latency-sensitive transactions (point lookups, single-row insert/update/delete). **Assumes a clean OLTP/OLAP split**: all reporting, analytics, and real-time aggregation run on a separate OLAP/streaming engine (e.g. ClickHouse), so analytical read fan-out and query-acceleration features are *out of scope*. Cost appears only as **price-performance**, not full TCO. WAL/CDC behavior is covered in the companion doc. Figures are vendor/benchmark claims (cited in §Sources), workload- and instance-class-dependent — directional, not guarantees.

## 1. Overview

This document compares Aurora PostgreSQL and RDS-for-PostgreSQL to decide which is the better **OLTP database** for our stack — a pure-OLTP comparison where OLAP is not evaluated, since all analytics run on a separate downstream engine. §2 scores each engine head-to-head on the dimensions pure OLTP stresses: commit latency, write throughput, random I/O, connection scaling, failover, and cost.

## 2. Head-to-head comparison

| Dimension | Aurora PostgreSQL | RDS-for-PostgreSQL | Caveat | Impact | Mitigation | Better choice |
|---|---|---|---|---|---|---|
| **Commit latency (single-row txn)** | • Commit needs a **4-of-6 quorum across 3 AZs** → the write path crosses AZ boundaries<br>• **Can never reach sub-millisecond** commit latency, regardless of instance size | • Single-node fsync to a **local** volume; io2 Block Express gives **sub-ms** commit<br>• A dedicated log volume cuts per-txn latency further | • *(Aurora)* The cross-AZ quorum is architectural — not tunable away<br>• *(RDS)* Sub-ms only with the right storage tier | • *(Aurora)* Latency-critical serial OLTP sees a hard floor above sub-ms<br>• *(RDS)* Wrong tier (gp2/underprovisioned gp3) → latency spikes | • *(Aurora)* Batch commits; exploit concurrency to amortize<br>• *(RDS)* io2 Block Express + separate log volume | **RDS** — only it can hit sub-ms commit latency |
| **Write throughput (concurrent)** | • Ships **only redo-log records**; no double-write buffer, no full-page checkpoint writes → low write amplification<br>• Up to **~3×** RDS, ~30% higher TPS at high client concurrency | • Full community write path (WAL + pages + double-write + checkpoints) to EBS<br>• Bounded by provisioned volume IOPS | • *(Aurora)* 3× is best-case; gain shrinks at low concurrency / small rows<br>• *(RDS)* Amplification consumes provisioned IOPS | • *(Aurora)* Best-in-class aggregate TPS for busy OLTP fleets<br>• *(RDS)* IOPS ceiling caps sustained write rate | • *(Aurora)* Benchmark your concurrency profile<br>• *(RDS)* Provision IOPS for peak write rate | **Aurora** — lower write amplification, higher TPS at concurrency |
| **Random read I/O (IOPS & latency)** | • Storage & I/O **auto-managed**, scales with the fleet; distributed layer + local caching offloads read I/O from the instance | • **Explicit** io2 Block Express: up to **256,000 IOPS / 4,000 MiB/s**, sub-ms, 99.999% durability; gp3 up to 64,000 IOPS | • *(Aurora)* No provisioned-IOPS knob → can't pin a hard I/O SLA<br>• *(RDS)* Must size IOPS correctly up front | • *(Aurora)* Opaque I/O ceiling; harder to guarantee p99 for random reads<br>• *(RDS)* Under-provision → throttling; over-provision → waste | • *(Aurora)* Use I/O-Optimized; load-test headroom<br>• *(RDS)* Provision io2 Block Express for a strict latency SLA | **Trade-off** — RDS pins guaranteed I/O; Aurora offloads it but opaquely |
| **In-memory working set (point reads)** | • Hot pages served from `shared_buffers` when the working set fits RAM | • Same — hot pages from `shared_buffers` | • *(Both)* Point-read latency degrades once the working set exceeds RAM | • *(Both)* Cache misses fall back to storage-tier latency | • *(Both)* Size the instance so the OLTP working set fits memory; monitor buffer cache hit ratio | **Tie** — identical when the working set fits RAM |
| **Failover recovery (RTO + warm cache)** | • Failover typically **< 30 s**<br>• **Cluster cache management** keeps a designated reader's cache warm → promoted writer avoids a cold-cache stall | • Multi-AZ **instance**: ~**60–120 s**, cold cache after promotion<br>• Multi-AZ **DB cluster**: faster (~35 s) | • *(Aurora)* Warm cache needs a same-class designated reader<br>• *(RDS)* Cold cache after failover → temporary latency spike | • *(Aurora)* Fast recovery **and** immediate warm performance<br>• *(RDS)* Minute-scale write outage + post-failover cold-cache slowdown | • *(Aurora)* Enable cluster cache management; front with RDS Proxy<br>• *(RDS)* Prefer Multi-AZ DB cluster; RDS Proxy to mask reconnection | **Aurora** — sub-30s and warm on promotion |
| **Connection scaling** | • High connection counts; **RDS Proxy** supported for pooling | • Same — **RDS Proxy** supported for pooling | • *(Both)* Postgres backend-per-connection memory is the true limit | • *(Both)* Connection storms exhaust memory without pooling | • *(Both)* Put **RDS Proxy** (or PgBouncer) in front | **Tie** — same pooling story |
| **Compute elasticity (spiky OLTP)** | • **Serverless v2** autoscales ACUs up/down with load<br>• Vertical/replica changes apply fast (shared storage) | • Vertical resize = reboot; no serverless tier | • *(Aurora)* Serverless v2 has a floor cost + scaling granularity<br>• *(RDS)* Scaling is slower and disruptive | • *(Aurora)* Absorbs bursty OLTP traffic without manual resize<br>• *(RDS)* Must pre-provision for peak | • *(Aurora)* Tune min/max ACUs<br>• *(RDS)* Pre-provision for peak; resize in windows | **Aurora** — automatic, fast elasticity |
| **OLTP read-only scaling (point-read offload)** | • Up to **15** replicas on shared storage; lag typically **ms–low seconds** | • Up to **5** streaming replicas (each own storage, primary overhead); Multi-AZ DB cluster adds 2 readers | • *(Aurora)* Replicas share one volume → not I/O isolation<br>• *(RDS)* Each replica taxes the primary + storage bill | • *(Aurora)* Cheap, low-lag read offload for read-heavy OLTP<br>• *(RDS)* Higher/variable lag; fewer, costlier replicas | • *(Aurora)* Reader endpoint; route read-after-write to writer<br>• *(RDS)* Cap replicas; monitor `ReplicaLag` | **Aurora** — more, cheaper, lower-lag replicas |
| **Autovacuum / bloat under update churn** | • Same community VACUUM/AUTOVACUUM mechanism; MVCC dead-tuple accumulation identical | • Same community VACUUM/AUTOVACUUM mechanism | • *(Both)* High UPDATE/DELETE OLTP churn → bloat if autovacuum lags | • *(Both)* Bloat inflates storage + degrades scans/index lookups | • *(Both)* Tune per-table `autovacuum_*` thresholds for hot tables; monitor dead-tuple ratio & `xmin` age | **Tie** — identical MVCC/autovacuum behavior |
| **Write-heavy saturation ceiling** | • Sustained bulk writes can saturate on **storage-quorum acks**; ceiling is high but opaque | • Ceiling = provisioned volume; a dedicated log volume + io2 raises it **predictably** | • *(Aurora)* Saturation point not directly tunable<br>• *(RDS)* Requires correct storage sizing to reach its ceiling | • *(Aurora)* Bulk write bursts may plateau below expectations<br>• *(RDS)* Hard but **knowable** ceiling | • *(Aurora)* Parallelize writers; I/O-Optimized<br>• *(RDS)* Separate log volume; max io2 Block Express | **Trade-off** — RDS ceiling is tunable/knowable; Aurora higher but opaque |
| **Price-performance (OLTP)** | • **Standard** (pay per I/O) vs **I/O-Optimized** (no per-I/O charge, higher instance rate)<br>• Strong TPS/$ at scale | • Provisioned instance + storage + IOPS; no per-request I/O charge | • *(Aurora)* **I/O-pricing trap** — Standard mode costly for I/O-heavy OLTP<br>• *(RDS)* Provisioned IOPS billed whether used or not | • *(Aurora)* Surprise bill on I/O-heavy Standard mode<br>• *(RDS)* Idle over-provisioning wastes spend | • *(Aurora)* Switch to I/O-Optimized above ~25% I/O spend<br>• *(RDS)* Right-size IOPS; gp3 unless io2 latency needed | **Trade-off** — Aurora scales cheaper; RDS is predictable & simpler to model |

## 3. Summary — which to choose for pure OLTP

Across the 11 dimensions the **Better choice** column tallies **Aurora 4 · Trade-off 3 · Tie 3 · RDS 1**. With OLAP separated out, the contest narrows: the two dimensions that usually run away in Aurora's favor (analytical read fan-out, tiered-cache acceleration) are gone, and OLTP steady-state dimensions (**working set, connection scaling, autovacuum**) tie. What's left divides cleanly — **Aurora owns aggregate throughput, elasticity, and failover recovery; RDS owns the latency-critical commit path and predictable, tunable I/O.**

| Priority driving the decision | Better choice | Because (from §2) |
|---|---|---|
| **Lowest single-transaction commit latency** | **RDS** | Local fsync on io2 hits sub-ms; Aurora's cross-AZ quorum has a hard floor above it |
| **Guaranteed / tunable random-I/O SLA** | **RDS** | io2 Block Express: explicit 256k IOPS / 4,000 MiB/s, sub-ms |
| **Predictable, easy-to-model cost** | **RDS** | Provisioned pricing; no per-I/O charge or I/O-Optimized decision |
| **Peak aggregate write throughput (high concurrency)** | **Aurora** | Redo-log-only writes → less amplification; ~3× TPS at concurrency |
| **Fast failover with no cold-cache stall** | **Aurora** | Sub-30s RTO + cluster cache management warm cache |
| **Spiky / unpredictable OLTP traffic** | **Aurora** | Serverless v2 ACU autoscaling |
| **Cheap read-only OLTP offload** | **Aurora** | 15 low-lag replicas vs 5 costlier ones |

**Net recommendation:**
- **Choose RDS-for-PostgreSQL** when the OLTP workload is **latency-critical and low-to-moderate concurrency** — small serial transactions where sub-millisecond commit and a guaranteed I/O SLA matter more than peak aggregate throughput, and where predictable cost is valued. This is exactly the profile pure-OLTP-with-strict-SLA systems often have.
- **Choose Aurora PostgreSQL** when the OLTP workload is **high-concurrency, bursty, or availability-sensitive** — many parallel transactions where aggregate TPS, sub-30s warm failover, and elastic scaling dominate, and per-commit latency can be amortized across concurrency.
- The three **Trade-off** rows (random I/O, write saturation, price-performance) turn on **elastic-scale vs. explicit-control**: Aurora if you want the platform to scale and recover for you; RDS if you want to pin, predict, and tune the numbers. Because the OLTP race is close once OLAP is removed, **benchmark the real transaction mix and concurrency** before deciding — the throughput multipliers are best-case and concurrency-dependent, and the commit-latency edge only shows at lower concurrency.
